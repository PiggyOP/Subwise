# Financial connection adapters

The product has no manual creation or statement-upload path. Public `POST /api/subscriptions` and `POST /api/import` return 410. Detected prices, cadence and merchant names cannot be edited through the public PATCH route. Only active/review tracking status is editable. Manual cancelled/requested status changes are rejected; see `CANCELLATION.md` for provider-confirmed execution.

## Actual integration status

There is **no production financial provider connected**. A separate [Setu AA sandbox adapter](./SETU-SANDBOX.md) now supports an explicitly allowlisted test account with provider-returned sample bank data. The generic card/UPI connector below is still a Subwise-owned adapter contract, not a bank, card-network, PhonePe, Google Pay or NPCI integration. It cannot be pointed directly at an arbitrary provider API and be expected to work. A contracted, authorized server-side adapter must implement that contract using the provider's real APIs and approved scopes.

Card-number collection and UPI-ID collection do not grant transaction access, so neither form exists. Authorization happens on the supported provider's screen. Neither a test Plus membership nor sample data unlocks real financial access.

## Configuration

- `FINANCIAL_CONNECTOR_URL`: HTTPS origin of the contracted server-side adapter.
- `FINANCIAL_CONNECTOR_SECRET`: backend-to-adapter bearer credential.
- `FINANCIAL_WEBHOOK_SECRET`: separate HMAC secret for adapter-to-Subwise delivery.
- `FINANCIAL_CONNECTOR_CHANNELS`: approved channels only, e.g. `card,upi`.
- `FINANCIAL_AUTH_ORIGINS`: comma-separated exact HTTPS origins allowed for authorization redirects. Defaults to the adapter's origin.

Never enable a channel unless your adapter and provider actually support that user's institution and the requested data. Availability in environment configuration is operator configuration, not proof of a user's connected account.

## Start authorization

Separate card and UPI connection creation has been removed: `/api/connections` now returns HTTP 410 after authentication and entitlement checks. The old contract below is retained only as integration documentation; existing feed ingestion remains compatible. The active bank sandbox uses `/api/setu/connections` instead.

The legacy adapter session contract was:

```http
POST https://YOUR_ADAPTER/sessions
Authorization: Bearer FINANCIAL_CONNECTOR_SECRET
Idempotency-Key: CONNECTION_UUID
Content-Type: application/json
```

```json
{
  "connectionId": "CONNECTION_UUID",
  "subject": "OPAQUE_SHA256_USER_REFERENCE",
  "channel": "card",
  "returnUrl": "https://YOUR_SUBWISE_DOMAIN/?connection_return=1"
}
```

The adapter creates an actual supported consent/authorization session with the contracted provider and returns:

```json
{ "authorizationUrl": "https://ALLOWED_PROVIDER_ORIGIN/REAL_SESSION" }
```

Subwise rejects insecure/unapproved redirect origins. Redirecting back to the app alone does not connect the account. The adapter must confirm successful authorization using a signed event.

The current return URL reopens the website; native app-to-app/deep-link return handling requires provider-specific implementation and device verification before release.

## Signed ingestion

Send a JSON POST to `/api/webhooks/financial` with:

- `x-subwise-timestamp`: current Unix seconds.
- `x-subwise-signature`: hex HMAC-SHA256 of `TIMESTAMP + '.' + EXACT_RAW_JSON_BYTES`, using `FINANCIAL_WEBHOOK_SECRET`.

Events outside a five-minute delivery window are rejected. Redeliver with a fresh signature/timestamp and the same event ID after transport failures. Event IDs are globally unique and deduplicated transactionally. Provider transaction IDs are unique per connection. Do not supply test data to production.

```json
{
  "id": "PROVIDER_EVENT_ID",
  "connectionId": "PREVIOUSLY_CREATED_CONNECTION_UUID",
  "status": "connected",
  "transactions": [
    {
      "id": "PROVIDER_TRANSACTION_ID",
      "merchant": "NETFLIX",
      "amount": 64900,
      "date": "2026-10-05",
      "currency": "INR"
    }
  ],
  "recurring": [
    {
      "id": "PROVIDER_RECURRING_STREAM_ID",
      "merchant": "iCloud",
      "amount": 90000,
      "cadence": "yearly",
      "nextDate": "2027-01-12",
      "currency": "INR",
      "status": "active"
    }
  ]
}
```

Amounts are integer paise; spending is positive, refunds negative. `transactions` and `recurring` are optional arrays. `recurring` must contain actual provider-identified recurring streams, never guesses generated by an AI or unverified merchant matches. Subwise uses this explicit recurrence to detect annual plans without waiting three years. A mandate's payment status must not be misrepresented as confirmation of the merchant contract's legal status.

When only transaction history is available, the existing detector requires three consistent dates and similar amounts; monthly/yearly patterns create records automatically. Stale history is marked for review. Provider streams take precedence over inferred records for the same merchant. Multiple streams at a merchant may require adapter-side disambiguation. Equal-time or out-of-order stream changes need provider-specific sequencing/reconciliation before production release; the contract currently does not supply a monotonic sequence number.

Revocation/error events have status `revoked`/`error` and no transactions or recurring records. A revoked connection cannot accept more data or silently reactivate; the user must authorize a new connection. Historical records remain visible as records of spending. The adapter must honor provider consent expiry and revocation, refresh only within granted scopes, and implement provider disconnection/deletion and reconciliation; those external operations are not implemented by the generic contract.

Dashboard clients refresh in the foreground approximately every 30 seconds. No automatic email/push delivery is implied. This is ingestion after an approved adapter integration, not direct universal card or UPI connectivity.

## India-specific references

[Setu's AA overview](https://docs.setu.co/data/account-aggregator/v1/overview) describes user consent between financial information providers and financial information users; production integration depends on eligibility, onboarding and coverage. [NPCI's UPI AutoPay requirements](https://www.npci.org.in/uploads/UPI_OC_No_223_FY_2025_26_Enhancement_of_UPI_Autopay_88b38535cb.pdf) cover participating PSP/app lifecycle flows and payer PIN authorization. These do not authorize an unaffiliated application to read any user's UPI account.
